# Puesta en marcha del piloto (no producción)
 
## 1. Firebase
Proyecto existente: tramite-discapacidad. No desplegar antes de revisar si contiene otros sistemas o reglas existentes. Crear app web, configurar Authentication (Email/Password + Email link y Google), dominios autorizados, bloqueo de altas no autorizadas según el piloto, App Check reCAPTCHA Enterprise. Crear Firestore en la región acordada; activar TTL en rateLimits.expiresAt. Configurar la facturación si Cloud Functions la requiere, alertas y presupuestos (no son límites duros), cuotas, IAM de mínimo privilegio y revisión de dependencias. Habilitar MFA para cuentas institucionales desde Workspace; validar que la política se aplica a todos los operadores. Denegar acceso directo mediante firestore.rules, siempre previa revisión de reglas preexistentes.
 
## 2. Drive y dos Apps Scripts
Usar la cuenta institucional autorizada de Salud (no la cuenta personal de TIC). Crear una carpeta raíz exclusivamente para expedientes piloto, sin acceso público ni compartición externa. Verificar permisos heredados; preferir unidad compartida institucional tras validar soporte de DriveApp/Drive avanzado y propiedad. Los subdirectorios se identifican por hash de expediente, no por nombre o cédula.
 
Crear dos proyectos de Apps Script separados, cada uno con su Code.gs, su appsscript.json y una copia de Common.gs. Configurar Script Properties ROOT_FOLDER_ID (misma raíz), HMAC_KEY (secreto aleatorio distinto de al menos 32 bytes por proyecto, codificado en texto), y PORTAL_URL (solo entrega; exactamente igual al parámetro de Functions). Desplegar como la cuenta propietaria Salud, probar permisos. Si la política Workspace permite web app accesible al backend sin OAuth, usar la validación HMAC, timestamp, nonce e idempotencia implementadas. Nunca publicar estas URL/secretos en el cliente ni habilitar acceso público al Drive. Si política Workspace prohíbe la exposición de web apps, sustituir el transporte por integración privada autenticada (Drive/Gmail API). CacheService es una mitigación temporal y no un registro durable de nonce.
 
## 3. Secrets y despliegue
Instalar dependencias en functions y generar lockfile; ejecutar npm run check y npm test, auditoría y emuladores antes de producción. No introducir claves por chat ni Git. Desde entorno autorizado: firebase functions:secrets:set ARCHIVE_URL, ARCHIVE_KEY, DELIVERY_URL, DELIVERY_KEY (cada comando por separado). El archivo functions/.env del entorno contiene ENABLE_PILOT=false y PORTAL_URL=https://tramite-discapacidad.web.app/ (ajustar al dominio aprobado). Configuración web pública en public/config.js, modo demo por defecto. No poner ENABLE_PILOT=true ni mode:pilot hasta probar autorización, email, privacidad del Drive, App Check, funciones, límites y conciliación con datos ficticios. Configurar en Firestore admins/{uid} (email exactamente igual a Auth, active:true, role:operator o supervisor) y pilotUsers/{uid} (active:true) para cada cuenta de prueba; no hay autoregistro de administradores.
 
Desplegar únicamente después de autorización y revisión de reglas: firebase deploy --only firestore:rules,firestore:indexes,functions,hosting --project tramite-discapacidad. El entorno puede requerir plan Blaze, cuotas de correo y almacenamiento compartido. No usar datos reales: esta versión exige una declaración de datos ficticios, lista de participantes y aprobación de un piloto cerrado.
 
## 4. Operación
El ciudadano confirma correo (enlace de Auth) y presenta la solicitud. Los archivos quedan en Drive; Firestore guarda identificadores, metadatos, estados y auditoría. La referencia SP-PIL no es radicado oficial. El operador cambia estado; supervisor, con nueva sesión Google de menos de 15 minutos, carga PDF oficial ya emitido por autoridad competente y confirma expediente y destinatario. El script archiva el certificado y notifica por correo con un enlace al portal; únicamente el titular autenticado con su cuenta puede descargarlo. No se envía un adjunto sensible no cifrado. No se debe reenviar ciegamente si hay incertidumbre; consultar expedientes en Drive y registro de correo. La cuota agotada deja el certificado archivado y requiere conciliación.
 
## 5. Bloqueantes antes de uso real
Aprobación de Salud/Jurídica/seguridad, política de tratamiento y retención documental (incluido caso de representante y menores), privacidad de Google Workspace, evaluación de riesgo e impacto, integración radicador oficial, política de verificación del destinatario/representación, antivirus/sandbox para insumos y certificados (verificar magic bytes y SHA no equivale a escaneo), cifrado y gestión de claves, manejo de carga incompleta, conciliación idempotente, avisos de recepción y subsanación, paginación administrativa, auditoría de accesibilidad WCAG 2.1 AA con usuarios reales, pentest y revisión de permisos/configuración del despliegue. Las pruebas no acreditan cumplimiento legal por sí solas.
 
No existe garantía de un sistema invulnerable. Esta rama es código piloto no desplegado. No recolectar expedientes clínicos reales.
