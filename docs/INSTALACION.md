# Puesta en marcha del piloto (no producción)
 
## 1. Firebase
Proyecto existente: tramite-discapacidad. No desplegar antes de revisar si contiene otros sistemas o reglas existentes. Crear app web, configurar Authentication (Email/Password + Email link y Google), dominios autorizados, bloqueo de altas no autorizadas según el piloto, App Check reCAPTCHA Enterprise. Crear Firestore en la región acordada; activar TTL en rateLimits.expiresAt. Configurar la facturación si Cloud Functions la requiere, alertas y presupuestos (no son límites duros), cuotas, IAM de mínimo privilegio y revisión de dependencias. Habilitar MFA para cuentas institucionales desde Workspace; validar que la política se aplica a todos los operadores. Denegar acceso directo mediante firestore.rules, siempre previa revisión de reglas preexistentes.
 
## 2. Drive y dos Apps Scripts
Usar la cuenta institucional autorizada de Salud (no la cuenta personal de TIC). Crear una carpeta raíz exclusivamente para expedientes piloto, sin acceso público ni compartición externa. Verificar permisos heredados; preferir unidad compartida institucional tras validar soporte de DriveApp/Drive avanzado y propiedad. Los subdirectorios se identifican por hash de expediente, no por nombre o cédula.
 
Crear dos proyectos de Apps Script separados, cada uno con su Code.gs, su appsscript.json y una copia de Common.gs. Configurar Script Properties ROOT_FOLDER_ID (misma raíz), HMAC_KEY (secreto aleatorio distinto de al menos 32 bytes por proyecto, codificado en texto), y PORTAL_URL (en ambos; exactamente igual al parámetro de Functions) y HEALTH_EMAIL (solo recepción; correo institucional autorizado de Salud). Desplegar como la cuenta propietaria Salud, probar permisos. Si la política Workspace permite web app accesible al backend sin OAuth, usar la validación HMAC, timestamp, nonce e idempotencia implementadas. Nunca publicar estas URL/secretos en el cliente ni habilitar acceso público al Drive. Si política Workspace prohíbe la exposición de web apps, sustituir el transporte por integración privada autenticada (Drive/Gmail API). CacheService es una mitigación temporal y no un registro durable de nonce.
 
## 3. Secrets y despliegue
Instalar las dependencias fijadas con `npm ci --prefix functions`. Ejecutar `npm --prefix functions run check`, `node --test tests/*.test.mjs` y `npm --prefix functions audit --omit=dev --audit-level=moderate`. Las pruebas de integración de Apps Script usan Drive y correo en memoria. Con Java 21, ejecutar también `firebase emulators:exec --only auth,firestore --project demo-discapacidad 'node --test tests/firebase-emulator.mjs'` con `GCLOUD_PROJECT=demo-discapacidad`. Después, ejecutar las pruebas del piloto autenticado con las dos integraciones institucionales. No introducir claves por chat ni Git. Desde entorno autorizado: firebase functions:secrets:set ARCHIVE_URL, ARCHIVE_KEY, DELIVERY_URL, DELIVERY_KEY (cada comando por separado). El archivo functions/.env del entorno contiene ENABLE_PILOT=false y PORTAL_URL=https://tramite-discapacidad.web.app/ (ajustar al dominio aprobado). Configuración web pública en public/config.js, modo demo por defecto. No poner ENABLE_PILOT=true ni mode:pilot hasta probar autorización, email, privacidad del Drive, App Check, funciones, límites y conciliación con datos ficticios. Configurar en Firestore admins/{uid} (email exactamente igual a Auth, active:true, role:operator o supervisor) y pilotUsers/{uid} (active:true) para cada cuenta de prueba; no hay autoregistro de administradores.
 
Desplegar únicamente después de autorización y revisión de reglas: firebase deploy --only firestore:rules,firestore:indexes,functions,hosting --project tramite-discapacidad. El entorno puede requerir plan Blaze, cuotas de correo y almacenamiento compartido. No usar datos reales: esta versión exige una declaración de datos ficticios, lista de participantes y aprobación de un piloto cerrado.
 
## 4. Operación
El ciudadano confirma correo (enlace de Auth) y presenta la solicitud. Los archivos quedan en Drive; Firestore guarda identificadores, metadatos, estados y auditoría. La referencia SP-PIL no es radicado oficial. El primer script envía avisos genéricos al solicitante y a Salud; si falla el correo, identifica estado pendiente o en revisión sin repetirlo ciegamente. El piloto cerrado acepta únicamente el perfil ficticio predefinido y los PDF de prueba descargables desde el portal. Functions verifica el contenido de cada archivo contra su SHA-256. El operador cambia estados, solicita un soporte de subsanación y consulta el historial de actuaciones. El titular autorizado recibe la solicitud en Seguimiento y presenta allí el PDF de prueba solicitado. El supervisor, con una sesión Google iniciada hace menos de 15 minutos, carga el PDF de certificado ficticio y confirma el expediente y el destinatario. El script archiva el certificado y notifica por correo con un enlace al portal; únicamente el titular autenticado con su cuenta puede descargarlo. No se envía un adjunto sensible no cifrado. No se debe reenviar ciegamente si hay incertidumbre; consultar expedientes en Drive y registro de correo. La cuota agotada deja el certificado archivado y requiere conciliación.
 
## 5. Bloqueantes antes de uso real
Aprobación de Salud/Jurídica/seguridad, política de tratamiento y retención documental (incluido caso de representante y menores), privacidad de Google Workspace, evaluación de riesgo e impacto, integración radicador oficial, política de verificación del destinatario/representación, antivirus/sandbox para insumos y certificados (verificar magic bytes y SHA no equivale a escaneo), cifrado y gestión de claves, manejo de carga incompleta, conciliación idempotente, avisos de recepción y subsanación, paginación administrativa, auditoría de accesibilidad WCAG 2.1 AA con usuarios reales, pentest y revisión de permisos/configuración del despliegue. Las pruebas no acreditan cumplimiento legal por sí solas.
 
No existe garantía de un sistema invulnerable. Esta rama es código piloto no desplegado. No recolectar expedientes clínicos reales.

**Demostración:** Settings → Pages → Build and deployment → Source → GitHub Actions. El workflow Pilot checks ejecuta pruebas estáticas y de navegador y publica solo public/ desde main cuando ambas pasan. El frontend público debe permanecer en modo demo, sin llamar a Firebase ni guardar documentos. URL esperada: https://adminterritorial-bit.github.io/TRAMITE-DE-DISCAPACIDAD/ (verificar el resultado de Deploy).

**Piloto cerrado en Firebase Hosting:** crear el entorno GitHub firebase-pilot, limitar a main y configurar revisores requeridos (si el plan lo permite). Configurar Workload Identity Federation en Google Cloud con condiciones para este repositorio, rama main y cuenta de despliegue de mínimos privilegios; sin claves JSON persistentes. Agregar variables del entorno GCP_WIF_PROVIDER, GCP_DEPLOY_SERVICE_ACCOUNT, FIREBASE_WEB_CONFIG (JSON público de la app), APP_CHECK_SITE_KEY y PILOT_PORTAL_URL (HTTPS, URL raíz final). Crear los cuatro secretos de Functions en Secret Manager mediante los comandos anteriores, no en GitHub. Confirmar que ambos Apps Script están desplegados y el almacenamiento es privado; comprobar roles, usuarios piloto, App Check y dominio en la consola. Ejecutar Deploy authenticated Firebase pilot desde main con confirmación PILOTO-CERRADO. Se debe comprobar que ningún otro sistema depende de las reglas Firestore existentes. El despliegue genera una configuración de entorno temporal que no se sube al repositorio. El modo piloto exige autorización explícita de cada UID y no acepta datos clínicos reales. ## 7. Reutilización de infraestructura municipal

Se portan y adaptan las funciones de carpetas, nombres y creación de blobs de [Mesa de Ayuda TIC - Archivos Drive](https://github.com/adminterritorial-bit/MESADEAYUDA/blob/c592cbcddffda90956aa20b5fe4a9990e190e050/apps-script-drive/Code.gs), y validación de correo del [script de notificaciones](https://github.com/adminterritorial-bit/MESADEAYUDA/blob/c592cbcddffda90956aa20b5fe4a9990e190e050/apps-script/Code.gs), conservando Google Workspace, DriveApp y MailApp. El contrato anterior autoriza sesiones Supabase y escribe ticket_attachments; no se invoca directamente desde Firebase ni se cambia la Mesa existente. Tampoco se hereda su opción DOMAIN_WITH_LINK. El trámite utiliza una carpeta independiente administrada por Salud, acceso general restringido y autorización HMAC del backend con roles Firebase. Se rechaza el acceso general no privado; además es indispensable revisar permisos explícitos e heredados y acceso de editores/managers, pues getSharingAccess no comprueba toda la ACL. En cada Apps Script del trámite, copiar Common.gs actualizado y ejecutar testConfiguration para comprobar propiedades, acceso general de carpeta y cuota sin crear archivos ni enviar mensajes. Las URL de despliegues del trámite y la autorización de Salud siguen pendientes; no se sustituye ni edita el despliegue existente de Mesa de Ayuda.
